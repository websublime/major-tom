## 1. Vision

Major Tom is a Claude Code / GitHub Copilot CLI plugin that defines and operates the software
development lifecycle of a project end to end: from product conception by the project manager,
through architecture conception by the architect, design definition and iteration by the designer,
construction by the technical team, and finally distribution.

The plugin is the harness: it brings the roles (static agents), the units of work (skills), the
compositions (workflows), and the supporting tools (memory, domain, documentation, roadmap,
visualization). The project being worked on keeps all resulting knowledge inside its own
directory. Nothing lives only in a session.

## 2. North star

Optimize for **correctness and completeness over speed**. This is a from-scratch rewrite of a
data-integrity tool: the knowledge the plugin persists is data whose integrity it must guarantee.
**Never simplify the solution to make progress.** At any simplification decision point, work
stops and the owner decides.

## 3. Problem statement

AI-assisted development today is session-bound and role-blind: context evaporates when the
session ends, every interaction is an undifferentiated "do X", and there is no persisted trail
from intention to release. Teams need a lifecycle discipline that agents follow the same way a
human team would, with distinct roles, explicit phase transitions, reviewable artifacts, and a
knowledge base that survives in the repository itself.

## 4. Goals

- **G1**: Define one canonical lifecycle every interaction runs on:
  `think → understand → decide → spec/plan → review → implement → verify → track → publish`.
- **G2**: Provide static agents covering the SDLC roles: product conception (project manager),
  architecture (architect), design definition and iteration (designer), construction (technical
  team), distribution.
- **G3**: Provide skills as atomic, individually invocable units of work.
- **G4**: Provide workflows as the only composition layer (workflows compose skills → agents).
- **G5**: Provide tools for: memory, domain, documentation, roadmap, visualization.
- **G6**: Persist all knowledge in the project directory: memories, docs, runs, monitors, logs.
- **G7**: Dual-publish: install-able in Claude Code and in GitHub Copilot CLI from this
  marketplace.

### Non-goals

- Not a project-management SaaS: no external server, no dashboard outside the repo.
- Not a replacement for the host runtime's own capabilities (task tracking, subagents,
  permissions): the plugin composes them, it does not reimplement them.
- No knowledge stored outside the project directory (no global caches as source of truth).

## 6. The lifecycle (core concept)

Every interaction, from a one-line bugfix to a full product phase, is an instance of the same
lifecycle. Phases are traversed in order; a phase may be trivially short, but it is never
skipped silently.

| # | Phase | Question it answers | Primary artifact (persisted) |
|---|---|---|---|
| 1 | **think** | What is actually being asked? | intent record |
| 2 | **understand** | What do we know: domain, codebase, constraints? | research/context notes |
| 3 | **decide** | Which direction do we commit to, and why? | decision record |
| 4 | **spec/plan** | What exactly will be built, in what steps? | spec / plan |
| 5 | **review** | Does the spec/plan hold up before we build? | review verdict |
| 6 | **implement** | Build it. | code + implementation log |
| 7 | **verify** | Does the result meet the spec? | verification report |
| 8 | **track** | What moved: roadmap, monitors, follow-ups? | roadmap/monitor updates |
| 9 | **publish** | Ship it and persist what was learned. | release record + memory updates |

Phase definitions above are a first proposal. Inputs, outputs, gates, and role ownership per
phase are iteration targets (see OQ-3, OQ-4).

## 7. Product surface

### 7.1 Agents (static)

The fixed role roster from section 5, shipped with the plugin. Agents are personas with
operating rules, not task scripts. Project-specific technical agents (e.g. a Rust engineer for
a Rust repo) are out of the static roster; see OQ-2.

### 7.2 Skills (atomic units)

One skill = one individual scope. A skill is never a composite: it does one lifecycle-shaped
piece of work and can always be invoked directly on its own (**FR-3**). The skill catalog
(names, one per phase or otherwise) is an open design question; see OQ-3.

### 7.3 Workflows (the composition layer)

Workflows are the only place where composition happens: a workflow sequences skills and
delegates to agents (skills → agents). Anything a workflow does must also be reachable by
calling its constituent skills individually (**FR-4**).

### 7.4 Tools

Supporting capabilities, each with a persisted footprint in the project directory:

| Tool area | Purpose |
|---|---|
| Memory | Persist and recall knowledge across sessions |
| Domain | Capture the project's domain model / ubiquitous language |
| Documentation | Produce and maintain project docs |
| Roadmap | Track phases, milestones, progress |
| Visualization | Render lifecycle state, roadmap, architecture views |

Implementation surface for tools (MCP server, bundled scripts, skill-embedded) is undecided;
see OQ-5.

## 8. Composability model

- **Atomicity rule**: every scope is individual, never composite. If a unit needs another
  unit's work, that is a workflow, not a bigger skill.
- **Composition rule**: workflows compose skills → agents. Workflows contain no logic that
  belongs in a skill.
- **Direct invocation rule**: every skill is invocable standalone, outside any workflow.

## 9. Execution model

### 9.1 The orchestrator invariant (INV-1, may never fail)

**The main session only orchestrates.** Coordination and iteration with the user is the whole
of its job. It never executes work itself: no implementation, no research, no artifact writing.
All execution is delegated per the working model of 9.2.

**Single exception**: the user explicitly says yes to the main session doing a given piece of
work. Consent is granted by the user in the conversation; it is never assumed and never
inferred. Its exact scope (per request? per task? is it recorded anywhere?) is OQ-11.

### 9.2 Delegation modes (configured by the onboard workflow)

| Mode | Shape | Selection |
|---|---|---|
| **team** (default) | A team of **minimum 3 agents plus one coordinator**. The main session hands work to the coordinator; the coordinator runs and closes the delegation and reports back. | Default working model. |
| **subagents** | The main session delegates directly to individual subagents; no team layer, no coordinator in the loop. | Only when the user explicitly selects it during onboard. |

INV-1 holds in both modes: the mode changes who receives the delegation, never whether the main
session may execute.

Both modes also share one worktree discipline (D38, extended by D40). Delegated work never
lands directly on the feature branch: it runs in a git worktree at
`.claude/worktrees/<feature-branch-slug>/` in the target project, the slug being the feature
branch name with `/` replaced by `-`, on a branch named `<feature-branch>-work`. One worktree
per delegated task, not one per agent inside a team. The review phase (section 6, phase 5)
sits between the worktree and the feature branch: work comes back for review once done, and
only then merges onto the feature branch; the worktree is removed after that feature branch's
PR merges, on an explicit instruction to the `vcs-operator` naming the target. The worktree
root is mechanism state, gitignored in the target project (section 11), and the
`git worktree add` is performed by the `vcs-operator` because the host's per-agent
`isolation: 'worktree'` option creates a harness-managed worktree per spawned agent, not one
per task at a fixed repo-relative path.

### 9.3 Enforcement

A rule that may never fail cannot be prose-only: evidence from the pre-reset eval program
(compliance-budget finding, rounds 11 to 16) is that prose rules lose to mechanical guards at
the bottom tier. INV-1 therefore requires a mechanical guard (e.g. a PreToolUse hook policy) in
addition to prose in agents/skills. The guard design (what exactly is blocked, how consent
unblocks it) is OQ-11.

## 10. Onboard configuration file

Everything the user decides during onboard is persisted in one configuration file. That file is
the single source of truth: every other surface (agents, skills, workflows, tools, hooks) reads
its behavior from it, never from memory of the conversation.

### 10.1 Envelope (D1 and D3 decided; remaining points are OQ-10)

| Property | Value |
|---|---|
| Path | **`.claude/major-tom.json`** in the target repo (decided, D1) |
| Format | JSON, validated plugin-side against a JSON Schema shipped at the plugin root (`config.schema.json`, D3). The config file carries no `$schema` pointer. |
| Writer | The `onboard` workflow. Re-running onboard updates the file (never silently overwrites: it shows a diff of changed answers). |
| Readers | Every plugin surface, including the INV-1 guard of 9.3. |
| Manual edits | Open point in OQ-10 (allowed and validated on read? or onboard-only?). |

### 10.2 Principles

- **P1, total capture**: every onboard answer maps to exactly one addressable key in the file.
  No decision lives only in prose or only in the conversation.
- **P2, versioned schema**: the file carries a `schemaVersion`; schema changes ship with
  explicit migrations.
- **P3, strict validation**: unknown keys and invalid values are errors, not warnings
  (data-integrity stance from the north star).
- **P4, decisions not state**: the config stores what the user decided; execution state (runs,
  logs, monitors) lives in its own persistence areas (section 11).

The `snapshot` block is required, and a config that lacks it is a fail-closed condition for
`plugins/major-tom/app/snapshot.js` rather than a case it defaults around (D49 point 3): the
default lives here precisely so that no reader carries a second copy of it, and the message the
reader produces says what is missing and that re-running the onboard writes it. The consequence
is stated rather than hidden, a project onboarded before the block existed cannot serve its
dashboard until it is re-onboarded, which is the situation D46's session-start hook already
reports.

Reserved top-level keys, to be defined when their open question closes: `memory` (OQ-6),
`specialists` (OQ-2), `tools` (OQ-5), `gates` (OQ-4).

Evaluated and rejected from the intake sketch (see decision log): `methodology` (D4),
`contracts` (D5), `sources.deferred` (roadmap of a different product, not a target-repo
decision), and `workspace.topology`, `workspace.shared`, `cloud` as top-level (duplicates
resolved by the single-file model, D6).

## 11. Persistence model

All knowledge produced by the plugin lives **locally in the target repository**, versioned
alongside the code; nothing lives only in a session or an external service. The rendered
context states this explicitly so every agent knows it.

- **memories**: cross-session knowledge
- **docs**: specs, decisions, PRDs, architecture
- **runs**: records of workflow/skill executions
- **monitors**: tracked signals and their state
- **logs**: execution trail

The root is decided: all five areas live under **`.knowledge/`** at the target repo root (D2).
The file format is decided (D28, closes OQ-6): `.knowledge/` is an **OKF v0.2 bundle**
(Open Knowledge Format, the Google Cloud spec). Every non-reserved `.md` is a concept with
YAML frontmatter carrying a required non-empty `type`; optional fields are used only when
truthful (an unknown actor is omitted, never invented; `stale_after` only when a concept
genuinely expires). The bundle root carries the reserved **`index.md`** (progressive
disclosure: one line per knowledge file, grouped by area, `okf_version: 0.2` in its
frontmatter) so sessions read the index instead of walking every file; **whoever writes a
knowledge file appends its index line in the same change**. Onboard brings the bundle to this
shape rather than creating it into an empty repository (D53): the `think` gate of D51 requires
a recorded intent before the onboard may run a single command, and the recorder of D36 creates
`.knowledge/`, `.knowledge/runs/` and, for a substantive intent, `index.md` and its first entry
as a side effect of recording, so by the time the onboard writes, the bundle usually exists and
carries live entries. Onboard therefore adds the missing area headings, the maintenance-rule
line and an entry for every file already present without one, and states that an area is empty
only where its directory is in fact empty. The onboard run record is a concept, no longer
necessarily the first one.
Per-area internal layout and the tracked vs. ignored split inside the bundle remain open in
OQ-7. The configuration file stays outside this root at `.claude/major-tom.json` (D1), and its
schema lives at the plugin root (D3).

**Mechanism state is not knowledge.** Everything the harness needs to operate, as opposed to
everything it learns, lives outside `.knowledge/` under `.claude/`, and is gitignored in the
target project (D38, D40): `.claude/worktrees/` (delegation worktrees, D38 and 9.2),
`.claude/session/` (turn-correlation state, one file per session, D36) and `.claude/server/`
(the dashboard's repo-local entry point, D32 as amended by D44). All three are
regenerated or recreated on demand and none of them is a project artifact. D43 adds the
generated dashboard artifact to that category and takes it out of the persistence root, on
the same reasoning: a file that carries no knowledge and only works with the mechanism
running is mechanism state, so `.knowledge/` goes back to holding only knowledge, which was
D2's intent. D44 then settles where it goes instead, and the answer is that nothing
substantial is copied into the target project at all: the application, server and page
alike, lives inside the plugin at `plugins/major-tom/app/` and runs from the versioned
install cache, and `.claude/server/` receives only a small launcher that resolves the highest
installed plugin version at run time, so updating the plugin updates the dashboard instead of
leaving a copy to age silently. Both moves are implemented since D48: no dashboard artifact is
written anywhere in the target project, and `.claude/server/` receives `launcher.js` and nothing
else, copied byte for byte from the plugin and taking no substitution of any kind.
The two things under version control stay under version control: `.claude/major-tom.json` is tracked because
it is the single source of truth for every plugin surface (D1, section 10), and `.knowledge/`
is tracked because it is knowledge versioned alongside the code (D2). The ignore rules are
written into the target's `.gitignore` by the onboard's Execute phase (section 12.5), not left
to prose.

## 12. Onboard workflow and templates

The `onboard` workflow (FR-8) is the writer of the configuration file and the installer of
the harness. Four phases:

| Phase | Responsibility |
|---|---|
| **Check** | Preconditions: target is a git repo; existing `.claude/major-tom.json` means re-onboard (diff mode, OQ-10); the `codebase-memory-mcp` MCP is available (D11/D13, name corrected by D50), which the check agent judges in prose rather than by any command (D50); when it is missing, the blocked report tells the user to install it from https://deusdata.github.io/codebase-memory-mcp/ before relaunching; the plugin's own runtime assets (`config.schema.json`, `templates/context.md.tpl`) exist under the plugin root (D23); detect `project.type`. |
| **Prepare** | Scan (stack, devops, topology, unit discovery, dependency graph) plus specialist candidates from the authorized source, inexact matches flagged (D24); ends stage 1 by returning the detected facts plus self-describing instructions to the main session (D21). |
| **Execute** | Stage 2, relaunched by the session with the interviewed config in `args`. Validate against `config.schema.json` (fail closed: an invalid config is never written), write the config, bootstrap `.knowledge/` (D2), which since D53 means bringing an existing bundle to its D28 shape and never assuming a virgin repository, render templates, install exactly the interview-confirmed specialist list via `agent-installer` (D22, D24), copy `app/launcher.js` byte for byte to `.claude/server/launcher.js` (D44 point 2 as implemented by D48), merge the managed dashboard entry into `.claude/launch.json` (D32), merge the project session defaults into the target's settings file (D37), write the mechanism-state ignore rules into the target's `.gitignore` (D40). Since D48 it neither generates a dashboard nor runs `app/snapshot.js` at all: the server computes the snapshot on demand and is that script's only consumer. Since D55 it also carries the residue quarantine, a step of its own between the writer and the render/install pair, which exists at all only when the session relaunched with `quarantine: true` and whose `failed` entries halt nothing, because cleaning up an older version's leftovers is not part of onboarding this project. |
| **Finalize** | Re-read and re-validate everything written, record the onboard itself as a run in the runs area, report to the user. Since D54 it no longer asserts file existence in prose at all: it runs `migration.js --verify .` (the artifact map, section 12.6) after the run record is written and reports what the script says, keeping only the two writes and the ajv revalidation, which the map deliberately does not re-implement. The assertions D48 added, `.claude/server/launcher.js` present and no dashboard artifact anywhere, are two of the entries the map now carries. |

**The interview is the schema**: every interview question is derived from a config key and its
schema `description`; enums provide the options. There is no separate question list to drift.
The `snapshot` block of 10.3 is written under that rule and is the first case where it decided
how a description is worded (D45 point 3, D49 point 1): its two `description` strings are the
help text the reader sees when asked for the window, so they say what the number does and what
the accepted range is rather than restating the key name, and each carries the `default` the
question proposes. A key's bounds therefore reach the user twice from one source, as the
question's stated range and as the schema validation the Execute phase runs before writing.

### 12.1 Templates

Templates live at the repository root, `templates/` (D16 as corrected by D19), as the single
shared source for **both plugins**. The context content is rendered once, into `AGENTS.md`,
the agent-instructions file both hosts read; `CLAUDE.md` is a thin wrapper importing it via
the `@AGENTS.md` directive (D26), so nothing is duplicated. Placeholder grammar
is a minimal mustache-compatible subset (variables, `#if`, `#each`), specified in
`templates/README.md`; the renderer is an Execute-phase agent. Authoring and runtime are
split (D23): the repo root is where templates are authored, and `scripts/sync-templates.js`
mirrors them verbatim into each plugin dir (`plugins/<plugin>/templates/`), because the
installed plugin cache contains only the plugin directory and paths outside it do not exist
after install. The synced copies are generated artifacts, never edited directly; the
`--check` mode of the sync script gates drift before publish.
Planned template set: the context template (exists) and one doc template per lifecycle artifact
(section 6). The dashboard is not among them since D44 point 1 as implemented by D48: it is an
application authored inside its own plugin, never a rendered template.

### 12.2 Dashboard

The dashboard is a **served application** (D43, sited by D44, cut over by D48). It is authored
inside its own plugin at `plugins/major-tom/app/`, a stated exception to the authoring-at-root
rule of D19 and D23 because the app is not shared with the Copilot plugin and would not exist
at runtime if authored at the root (D44 point 1): `server.js` (Node's own `http`, no framework,
D44 point 5), the generated `dashboard.html` built from the `dashboard/` authoring split by
`scripts/build-dashboard.js` (D34), `snapshot.js` with its vendored parser (D47), and
`launcher.js`. Dependencies are vendored as readable source with version and SHA-256 recorded,
and nothing is installed in the target project or in the plugin (D44 point 4).

Nothing substantial is copied into the target project (D44 point 2, implemented by D48): no
snapshot is embedded in any file, no dashboard artifact is written anywhere in the target, and
`.claude/server/` receives `launcher.js` and nothing else. The data island, `file://` viewing
and the byte caps went with that cut-over, and the page is viewable only by running the server.

The server serves three targets and nothing else, on 127.0.0.1, GET only: `GET /` is the built
page beside it, `GET /api/snapshot?days=<n>&limit=<n>` computes the snapshot for the served
repository on that request over the window the request asked for, and
`GET /api/knowledge/body?id=<id>` returns the body of the one concept that opaque
id addresses. Anything else is 404, any other method is 405, and every non-success response is
JSON `{error}` (D48 point 9). The two window parameters are optional and independent, an absent
one leaving the configured default in force, and the server holds no default and no bound for
either (D45, D49 points 1 and 4): it converts a digits-only value and passes anything else
through unconverted, so `snapshot.js` is the single producer of the sentence that names the
parameter, the value received and the accepted range. A refused parameter is answered 400 and a
broken repository 500, told apart by `SnapshotError.parameter` and never by matching the message
text (D49 point 5). A query parameter neither route reads is ignored rather than refused (D49
point 6). No path parameter is ever taken from a request and the server
holds no knowledge path at all, the body lookup living in `snapshot.js` (D43 point 8 as
implemented by D48 point 1); routes are compared literally and never parsed with the WHATWG
`URL` constructor (D48 point 6); there is no cache and no separate recompute verb, the page's
refresh control being the same `GET /api/snapshot` issued again (D43 point 5, D48 point 2); and
the directory-serving mode the old static server carried is gone (D48 point 5). The port is the
explicit argument, else `PORT`, else 4242, with `0` honoured as `bind(2)` defines it and every
other invalid value refused at startup (D48 point 8).

The client is six hash-routed views (overview, timeline, roadmap, git history, knowledge,
config) that boot asynchronously: `api.mjs` owns transport, `data.mjs` derives from a stored
snapshot instead of load-time constants, and a failed fetch renders an explicit error state
naming the request, repeating the server's own message and offering a retry (D43 point 7, D48
point 7). The header pill carries the time of the last computation with the refresh control
beside it, and beside that pill sits the window control of D45: two fields and an explicit
apply, in the header rather than in a view because the window cuts two of the six (D49 point 7),
submitting both numbers in one request rather than fetching as the fields change (D49 point 9),
returning to the configured default on a reload because the chosen window is never stored (D49
point 8), and rendering a refused window as an inline correction beside the control while the
view, its data and the refused value all stay in place (D49 point 10). The knowledge view
fetches one body at a time by its id, and its tree groups
concepts by their first path segment rather than by the five fixed areas, so no concept the
bundle holds is unreachable (D48 point 10).

### 12.3 Invocation and runtime facts

The entry point is closed (D20): scripts in the plugin's `workflows/` directory are a native
host surface, no skill wrapper needed (docs plus owner's local test). Plugin workflows are
namespaced: `meta.name: 'onboard'` runs as `/major-tom:onboard`. Requires Claude Code
v2.1.154+; organizations can disable workflows entirely, in which case the command does not
exist (known limitation). The full script API contract lives in
`plugins/major-tom/workflows/README.md`.

Two runtime constraints shape the design:

- **The script has no filesystem access.** Every write (config file, `.knowledge/`
  bootstrap, rendered templates, the `.claude/server/launcher.js` copy) is performed by
  agents the script spawns; the script only coordinates. This is INV-1 applied to the
  workflow itself.
- **No mid-run user input.** Only agent permission prompts can pause a run, so the
  schema-walk interview cannot happen inside the workflow. Resolution (D21, closes OQ-14):
  a two-stage protocol behind one user-visible command. Stage 1 (Check + Prepare) returns
  the detected facts plus self-describing instructions; the **main session** conducts the
  interview (it is the only surface with user interaction, and per INV-1 coordinating with
  the user is exactly its job) and relaunches the workflow itself with
  `args = { stage: "execute", config, quarantine }`. The user never launches stage 2 by hand.
  The same constraint is what fixed where the residue quarantine of D55 asks its one
  question. Execute can put no question to anyone, so the consent for the whole quarantine
  plan is collected in the interview and arrives as one boolean on the relaunch, and
  anything that is not an explicit `true` is read as a no.

A third runtime fact closed the path-resolution question (D23): `${CLAUDE_PLUGIN_ROOT}` is
not substituted in workflow scripts or `agent()` prompts, only in plugin agent/skill
content, hooks, and MCP/LSP configs. The workflow therefore resolves paths through the
`onboard-check` plugin agent: its markdown body carries the substituted plugin root, it
reports that absolute path (plus the preconditions), and the script threads it into the
validate/render/finalize prompts. Stage 2 re-runs the check instead of trusting anything
the session passed in `args`.

Still open in OQ-12: the merge policy for an existing `CLAUDE.md` (managed blocks proposed
in `templates/README.md`).

### 12.4 Project session defaults

The Execute phase also writes the target project's Claude Code session defaults (D37):
`env.CLAUDE_CODE_SUBPROCESS_ENV_SCRUB: "1"` (sandboxing hardening forced on by default),
`env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: "1"` (the flag behind the team delegation mode
of 9.2), and `alwaysThinkingEnabled: true` (extended thinking on, matching the north star).
The write is done by `templates/settings-merge.js`, the same discipline as the D32 launch
merge: the script owns the file choice (`.claude/settings.local.json` when the project
already has one, else `.claude/settings.json`, else a fresh `.claude/settings.json`), only
the three managed keys are written, every other key and every other `env` entry is
preserved, and an existing file that does not parse, that is not a JSON object, or whose
`env` is not an object is a hard failure that writes nothing. Finalize re-reads the file the
merge targeted and verifies the three values landed.

### 12.5 Mechanism-state ignore rules

The Execute phase also writes the target project's `.gitignore` (D40), so the mechanism-state
paths of section 11 are ignored by a mechanism rather than by prose: `.claude/worktrees/`
(D38), `.claude/session/` (D36) and `.claude/server/` (D32). `.claude/major-tom.json` (D1) and
`.knowledge/` (D2) are never listed: they are tracked on purpose.

The write is done by `templates/gitignore-merge.js`, Node with no dependencies, the same
discipline as the D32 launch merge and the D37 settings merge. It owns one managed block,
delimited by the line markers `# major-tom:begin` and `# major-tom:end`, and nothing outside
it. Policy: the file is created with the block when it does not exist; only the block content
is replaced when both markers are present; the block is appended when the file exists without
markers. Every other line of the file is preserved byte for byte, including entries that
duplicate the managed ones: existing user entries are never removed and never deduplicated,
because the script's mandate is its own block, not the rest of the file. Re-running it is
idempotent.

Failure modes, all fail-closed with nothing written: malformed markers, meaning a begin
without an end, an end without a begin, an end before its begin, or a duplicate of either
marker, and a file that cannot be read. A malformed marker set means the script cannot tell
which lines it owns, so it refuses rather than guess. Finalize re-reads the target's
`.gitignore` and verifies the managed block landed with the three paths in it.

### 12.6 The artifact map

Everything the onboard writes into a target project is declared in one place, `plugins/major-tom/migration.js` (D54), and every consumer reads it from there rather than restating it. It sits at the plugin root beside `config.schema.json` for the same reason that file does: it is the plugin's declaration about the target project, not a template and not application code, and the install cache carries only the plugin directory. Node, CommonJS, zero dependencies, the discipline of the three merge scripts.

The map has 25 entries covering the config file, the persistence root with its five areas and their `.gitkeep` files, the bundle index, the onboard run record, the recorder's `intents.log`, intent concepts and session records, `AGENTS.md` and `CLAUDE.md`, the installed specialists and the directory they live in, the managed `launch.json` entry, the managed settings keys, the managed `.gitignore` block, the launcher and the directory it sits in, and the delegation worktrees. Each entry carries the path (with `<persistence.root>` resolved from the target's own config), the mechanism that writes it, its kind, whether it is tracked, ignored or not decided, whether the plugin shares the file with its owner, and how the artifact is proved to be ours. That last field is the one that makes the map verifiable rather than a list of guesses, and where nothing inside an artifact can prove authorship it says so instead of claiming a proof it does not have.

Five modes since D55, of which exactly one writes. `--verify <repo>` is what the Finalize phase runs. `--assets` prints what must exist under the plugin root, and is the single source both the workflow's blocked report and check 4 of `onboard-check` derive from, those two having been hand-written copies that drifted apart. `--check` proves the map does not lie about the plugin itself, including that the mechanisms still write the markers, the managed entry name and the managed keys the map declares, and is a standing pre-commit gate beside the build and sync checks. `--plan <repo>` reads `onboard.pluginVersion` from the target, reports the transitions that apply and, for each residue subject it finds, whether the declared evidence actually holds for the file sitting there. `--quarantine <repo>` is the writing mode, and all it writes is a rename; `onboard-check` derives the workflow's `residuePlan` from `--plan`, and the Execute phase runs `--quarantine` only where the user consented.

Transitions are declared, never derived: a diff of the map at two versions cannot tell a file that moved from a file deleted plus a file created, and those migrate in opposite ways. Three species, six entries today, listed in D54. Since D55 the residue species carries `evidence` beside `detect`, an array of predicates read by the same evaluator the map entries use, and `remedy` reads `quarantine` where it used to read `delete`, which had become the name of a mechanism that does not exist.

Four rules govern that one writing mode, all of them D55. **The plugin never deletes.** Residue is renamed in place to `<path>.retired`, which keeps the file exactly as visible to git as it already was, tracked if it was tracked and ignored if it was ignored. **Nothing is touched without proof of authorship.** A file at a declared residue path whose evidence fails is reported with the failing predicate and left alone, as is anything the map cannot prove is ours. A destination that already exists is skipped rather than overwritten. **The plugin never cleans the quarantine.** A `.retired` file belongs to the user from the instant it exists, and no mode reads it, rewrites it or removes it. **The map stays honest.** Residue still on disk is still `RETIRED` and still counts as a problem, whether the user declined, the evidence failed, the destination was taken or the rename failed; the map reports what is on disk and knows nothing about consent, and the onboard's run record is what tells those four apart from an unexplained defect. A quarantined file is reported as the lowercase status `quarantined`, which is not a problem, and is exempted from the unexpected-file sweep of a directory the plugin owns whole, so the remedy does not install a permanent new fault.

`--check` gates that mechanism at declaration time. A residue must declare non-empty evidence, may not use the `none` predicate that is an honest answer for a reporting-only map entry, and must declare `remedy: quarantine`; anything that is not a residue may not carry evidence at all.
