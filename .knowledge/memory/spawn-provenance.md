# Spawn provenance is measurable

Measured 2026-07-27 on claude 2.1.220, in this repo.

A subagent CAN spawn a subagent, and the harness documents the rule. By default a subagent spawns its own up to THREE layers below the main conversation; at the limit Claude Code withholds the `Agent` tool from every subagent except a fork, so the one at the limit does the work itself and returns a summary. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` changes the limit and `1` turns nesting off. The default moved recently and is version dependent: five and unchangeable through v2.1.216, ONE in v2.1.217 and v2.1.218, three from v2.1.219. Count the layers before designing a fan-out. A driver invoked as a skill in the main session leaves room (act is layer 1, its gatherers and attackers layer 2); a driver that is itself spawned puts act's gatherers at layer 3, the limit, where they can delegate no further.

Confirmed by probe: a headless `claude -p` session asked for a nested spawn produced one, and the inner agent returned its result. To reproduce, run a top level headless session capturing `--output-format stream-json --verbose` to a file, then count Agent tool_use events in that stream.

Spawns form a TREE in the stream, not a flat list. Both spawn events appeared in the parent stream, told apart by `parent_tool_use_id`: null for the one the main session issued, the outer agent's tool_use id for the one the subagent issued. This corrects the note at `docs/specs/gc-iron-spec.md` line 224 (a Historical document, deliberately left unchanged) that a subagent's internal steps do not reach the parent transcript: its own spawn calls do, with parent attribution. A judge can therefore count a delegation's fan-out, not only its top level spawn.

Observed once, cause NOT isolated: an agent running inside a Workflow got "Task exists but is not enabled in this context" for both `Agent` and `Task`. That is a single uncontrolled observation, and the documented depth limit is an alternative explanation the probe did not rule out. Do not treat "Workflow agents cannot spawn" as established; treat it as a reason to verify the depth of a delegation chain before relying on it.

Two harness hook events serve provenance: `SubagentStart` (fires when a subagent is spawned) and `SubagentStop`, both matching on agent type. Hook payloads carry `agent_id` ONLY when the hook fires inside a subagent call, which is precisely what makes it a discriminator. So a `SubagentStart` hook can write a spawn ledger the model cannot author, and a `PreToolUse` hook on `Edit|Write` can block main thread edits by testing for the absence of `agent_id`. That is the mechanical instrument the [delegation-as-prose](delegation-as-prose.md) diagnosis lacked.

Still unverified: the calibration precondition in `eval/archive/workflow-s10.js` guards one specific leg, whether a WORKFLOW AGENT's Bash can launch a nested `claude -p` that spawns. The probe above was a top level headless run, so the grep the precondition uses returns 2 on it, but the leg it exists to test was not exercised. Run the precondition itself before scoring any round that depends on it.
