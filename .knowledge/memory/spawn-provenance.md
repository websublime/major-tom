# Spawn provenance is measurable

Measured 2026-07-27 on claude 2.1.220, in this repo.

A subagent CAN spawn a subagent, and the harness documents the rule. By default a subagent spawns its own up to THREE layers below the main conversation; at the limit Claude Code withholds the `Agent` tool from every subagent except a fork, and a fork at the limit keeps `Agent` in its inherited tool list but the tool returns an error instead of spawning, so the exception buys no extra layer. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` changes the limit and `1` turns nesting off. The default moved recently and is version dependent: five and unchangeable through v2.1.216, ONE in v2.1.217 and v2.1.218, three from v2.1.219.

Count the layers before designing a fan-out, remembering that layers are counted BELOW the main conversation and that a skill invoked in the main session is not a layer. Two chains, at the default of three:

- driver invoked as a skill in the main session: main (no layer) spawns act (1), act spawns its gatherers and attackers (2). One layer still free.
- driver itself spawned: main spawns the driver (1), the driver spawns act (2), act spawns its gatherers (3). Layer 3 is the limit, so those gatherers can delegate no further.

Confirmed by probe: a headless `claude -p` session asked for a nested spawn produced one, and the inner agent returned its result.

To reproduce, three things matter and two of them are easy to drop. The prompt must be explicitly two level ("spawn ONE subagent whose own instructions are to call the Agent tool and spawn a further subagent that replies BANANA, then report its reply verbatim"), because a one level ask never exercises the nesting. Pass `--allowedTools Agent`. Capture with `--output-format stream-json --verbose`, redirecting stdin from `/dev/null` to skip a 3 second stdin wait.

CORRECTION, measured 2026-07-30 on claude 2.1.220 with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` confirmed set in the shell. The older claim here and in `docs/specs/gc-iron-spec.md` and `eval/archive/workflow-s10.js` (both left unchanged as archive) was that without the allowlist the spawn tool prompts and, headless, is denied. It does NOT. A headless run given `--allowedTools Read`, with `Agent` absent from the allowlist, spawned anyway: one `"name":"Agent"` event and the subagent's reply returned. `--allowedTools` is a permission allowlist, not an availability restriction: omitting a tool from it does not withhold that tool. Be precise about the scope, because the two halves differ by tool. `Agent` was not permission gated here and ran unlisted, while `Write` WAS gated: a run with no allowlist could not create a file at all, so for that tool the prompt is effectively a block. What actually withholds `Agent` is `--disallowedTools Agent`: zero spawn events, and the executor reports it cannot spawn. `--disallowedTools Agent` alone suffices on this version; adding `Task` changes nothing.

The half of the old record that SURVIVES: `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` does force the permission mode to default and does make `--permission-mode bypassPermissions` a no-op. Measured the same day: with the variable at its ambient `1`, a bypass run still could not write.

THE TOOL HAS TWO NAMES AND THEY DISAGREE WITHIN ONE SESSION. Measured across twelve headless runs on 2.1.220: the `tools` array of the `system` init event named the spawn tool `Task`, while the `tool_use` events the same sessions emitted named it `Agent`. Both names occur, and which one appears is not stable across sessions or between the offered list and the emitted call. Counting spawns by grepping a single name returns zero and reads exactly like a behavioral finding. This nearly published a false null twice: once on a whole scored round, once on the probe that followed it. Always parse `tool_use` events for BOTH names, and read availability from the init event's `tools` array rather than inferring it from what was called.

Harness recipe for a headless eval cell that must both act and have its delegation controlled, measured end to end on 2.1.220. Set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0` and pass `--permission-mode bypassPermissions`, which restores full tool use without enumerating tools (an enumerated `--allowedTools` also works but silently handicaps a run for any tool the list forgets). `--disallowedTools` still holds under bypass, verified in both directions, so delegation is controlled by that flag alone and the two cells stay identical except for it.

This matters most in the direction people do not check. Enabling a spawn is self-verifying, because a missing spawn is visible. Building a spawn-FREE control cell from the old sentence silently produces a cell that still spawns, and the round measures nothing. Any condition that must not delegate uses `--disallowedTools`, and the round verifies zero spawn events in that cell's transcript before scoring it. Then discriminate on `parent_tool_use_id`, NOT on a count: two Agent events also occur when the main session spawns two siblings, and only a non-null `parent_tool_use_id` proves one spawn came from inside another.

Spawns form a TREE in the stream, not a flat list. Both spawn events appeared in the parent stream, told apart by `parent_tool_use_id`: null for the one the main session issued, the outer agent's tool_use id for the one the subagent issued. This EXTENDS the note at `docs/specs/gc-iron-spec.md` line 224 (a Historical document, deliberately left unchanged) rather than correcting it: that note already carves out "its spawn call and returned result" as visible. What is new here is the parent attribution, which is what turns a list of spawns into a tree. A judge can therefore count a delegation's fan-out, not only its top level spawn.

Observed once, unexplained: an agent running inside a Workflow got "Task exists but is not enabled in this context" for both `Agent` and `Task`. Do NOT treat "Workflow agents cannot spawn" as established. It is a single uncontrolled observation, and the documentation argues the other way: it counts "subagents that a workflow's agents spawn with the Agent tool" toward the session limit, which presumes they can. The depth limit does not explain it either, since that failure shape is the tool being withheld from the list, or present and erroring for a fork, and neither is the message observed. Verify before relying on it in either direction.

Two harness hook events serve provenance: `SubagentStart` (fires when a subagent is spawned) and `SubagentStop`, both matching on agent type. Hook payloads carry `agent_id` ONLY when the hook fires inside a subagent call, which is precisely what makes it a discriminator. So a `SubagentStart` hook can write a spawn ledger the model cannot author, and a `PreToolUse` hook on `Edit|Write` can block main thread edits by testing for the absence of `agent_id`. That is the mechanical instrument the [delegation-as-prose](delegation-as-prose.md) diagnosis lacked.

Still unverified: the calibration precondition in `eval/archive/workflow-s10.js` guards one specific leg, whether a WORKFLOW AGENT's Bash can launch a nested `claude -p` that spawns. The probe above was a top level headless run, so the grep the precondition uses returns 2 on it, but the leg it exists to test was not exercised. Run the precondition itself before scoring any round that depends on it.
